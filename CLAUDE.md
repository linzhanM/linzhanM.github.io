# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a personal academic homepage for Linzhan Mou, deployed as a GitHub Pages static site at the custom domain `linzhanmou.com`. There is no build system, no package manager, and no server-side code — the one build step in the repo is the LaTeX résumé (see `resume/latex/`).

**Domain**: the root `CNAME` holds `linzhanmou.com`. Five hostnames — `www`, both `http` variants, and `linzhanm.github.io` — each single-hop 301 to it with the path preserved, so old links keep working. `linzhanmou.com` is the only host that serves content. **Every absolute self-link must use it** (`index.html`, `resume/`, `dimo/`, `unimate/`, `sitemap.xml`, `robots.txt`, `resume/latex/resume.tex`), otherwise internal navigation pays for a redundant DNS+TLS handshake (~2× the load time). Don't delete `CNAME` — it is the switch for the whole redirect setup.

## Development

To preview locally, serve the directory with any static file server:

```bash
python3 -m http.server 8000
# then open http://localhost:8000
```

To deploy, commit changes and push to `main` — GitHub Pages serves the branch automatically, usually live within ~1–2 minutes. `main` **is** the deploy branch, so a feature branch does not deploy.

There is no Git LFS setup and no `.gitattributes` — all media is committed directly (videos, images, PDFs, `.glb` models). GitHub Pages cannot set response headers here, so anything header-based (HSTS, `X-Robots-Tag`) is not available; `robots.txt` and `<meta>` tags are the only levers.

## Architecture

**No framework**: no templating, routing, or JS framework anywhere. Every page is hand-written HTML.

**CSS hybrid** (homepage + résumé): local stylesheets layered on a CDN-loaded Bootstrap 4 **CSS** grid (no Bootstrap/jQuery JS — neither page loads any). `static/custom-navbar.css` owns *all* navbar chrome: the sticky bar, the mobile burger, the ≥1024px flex layout, the `.nav-section` eyebrow labels, and the `.nav-keypoint` accent dot. `static/styles.css` holds the design system: a `:root` block of design tokens, base typography, and the hero / section / publication / experience / footer styles. Fonts are Fraunces (display — name and section headers) and Source Serif 4 (body), from Google Fonts; `.pub-title` overrides to Palatino Linotype. The homepage's third-party loads are exactly: Bootstrap 4 CSS, Font Awesome 5 (`.fab`/`.fas` icons in `.hero-links`), Academicons (`.ai-google-scholar`), Google Fonts, StatCounter, and four `img.shields.io` GitHub-star badges — nothing else. The star counts are **plain `<img>` badges**, which is why the old `buttons.github.io/buttons.js` was removed: it acts only on `class="github-button"` elements, and shields.io had already replaced it. Don't re-add a script for star counts. `resume/index.html` deliberately drops the two icon stylesheets, because its contact links say "Scholar"/"GitHub" in words and the icons were labelling what was already labelled.

The `:root` tokens are a system, not a loose bag — stay on them rather than hard-coding a value:
- **Surfaces** `--ivory-light/-medium/-dark`, `--accent-bg`.
- **Ink, four tiers** `--text-primary/-secondary/-tertiary`, each documented with its contrast ratio (all ≥4.5:1 AA on `--ivory-light`).
- **Radius, three steps** `--radius-sm/-md/-lg`, all fixed px on purpose — percentages resolve against the box and turn non-square elements into shape-shifting ellipses. A circle (the nav keypoint) is a shape, not a step, and stays `50%`.
- **Elevation, two layers each** `--shadow-plate` / `--shadow-lift` — a tight contact shadow plus a diffuse ambient one, so media reads as set *onto* paper rather than floating.
- **Accent** `--accent: #E77500` (Princeton orange) is for **geometry only** — rules, borders, the keypoint, link underlines. Never the colour of running text: orange dark enough to pass AA on ivory is orange gone brown.

Three rules to keep in mind when editing CSS here:
- `styles.css` loads **after** `custom-navbar.css`, so a `.navbar` rule placed in `styles.css` silently wins. Keep navbar rules in `custom-navbar.css`. `styles.css` currently has none — verify before adding.
- The one sanctioned exception: `static/resume.css` re-declares `.navbar-inner` (and hides `.navbar` in print). That is not navbar chrome, it is the résumé page *opting out* of it — it has a single link and no burger, so the flex row has to hold at every width instead of only ≥1024px. The file documents this at the rule.
- Bootstrap defines `.navbar` as `display: flex` with `padding: 0.5rem 1rem`; `custom-navbar.css` zeroes that padding and gives `.navbar-inner` `width: 100%` so it doesn't collapse to its content. Don't remove either without re-checking the layout.

**Cache busting**: the local `<link>`/`<script>` tags carry a `?v=N` query, because GitHub Pages caches aggressively. **`styles.css` and `custom-navbar.css` are referenced from two files — `index.html` and `resume/index.html` — so bump `N` in BOTH** whenever you edit either stylesheet or `nav.js`, or returning visitors keep the old file. Keep the two files' numbers **equal** for a given stylesheet: same file at the same URL means one shared cache entry instead of two fetches. Both are at `v=37`; they had drifted to 37/34 once, which left `/resume/` serving a stale `styles.css`. `resume.css` is loaded only by the résumé page and carries its own counter (`v=4`). `dimo/` and `unimate/` deliberately carry no `?v=` at all; their CSS/JS is per-page, so renaming isn't needed.

**Styling convention**: `index.html` and `resume/index.html` carry **no inline `style=` attributes and no `<br>` spacers** — every rule lives in a stylesheet behind a named class (`.hero*`, `.page-section`, `.exp-*`, `.resume-*`, `.site-footer`). Both files are currently at zero of each; keep it that way. Sections are `<section class="container page-section">`: the Bootstrap `.container` is required, because `.row` uses −15px side margins that need the container's padding to cancel them.

**JavaScript** (homepage):
- `static/nav.js` — toggles `.is-active` on `.navbar-burger` / `#navbar-main` for the mobile menu, and drives the navbar keypoint by writing `--kp-x` / `--kp-o` onto `.navbar-sections` (easing stays in CSS). Three non-obvious details, each commented at the code: the "current section" probe line **sweeps downward** as you near the bottom of the page rather than sitting under the navbar, because `#Experience` is too close to the end for its heading to ever climb that high; a document-level click listener re-measures on a `setTimeout` (not rAF, which is suspended in background tabs) because expanding an abstract moves every section below it; and the mobile menu closes itself after a jump. Nav links are plain anchors, so navigation degrades without JS.
- Inline JS in `index.html` — `display(id)` toggles a publication's abstract; an `IntersectionObserver` (`rootMargin: 200px`) plays/pauses `video.lazy-video`; a one-liner fills `#copyright-year`. StatCounter (project `12925377`) loads at the end of `<body>` — the same project also loads on `unimate/`, but not on `dimo/` or `resume/`.

**Homepage nav**: the rail holds three links — About, Research, Experience. `#About` is not a section; it is the `id` on `.hero` itself (`<div class="container hero" id="About">`). `#Publications` is labelled "Research". `#Service` exists as a section but is deliberately **not** in the nav, and the Resume link is commented out with a note explaining that it isn't a section on this page so `nav.js` would skip it.

**Publications pattern**: Publications live under `#Publications` (headed "Recent Research"; the `id` is still `Publications`), split into `.section-h3` subsections `#Vision` ("Vision & Graphics") and `#Robotics` ("Robotics & RL"). Each entry is a `.pub-row.row`: a video/image thumbnail in `.col-md-3` and details (`.pub-title` / `.pub-authors` / `.pub-venue` / `.pub-links`) in `.col-md-9`. Abstract text is hidden in a `<div id="*-abs" class="pub-abstract">` block, toggled by `onclick="display('*-abs')"`. All four live thumbnails carry `class="lazy-video"`, so the observer plays them only while on screen; the Robotics pair (`ttt-parkour`, `vr-robo`) additionally sets `preload="none"` so they don't fetch until then, while the two above the fold (`unimate`, `dimo`) keep `preload="metadata"` and `autoplay`. "Let Occ Flow" is isolated in a `<template>` (parsed but never rendered, and its video has no `lazy-video` class since it never displays); its `assets/letoccflow.mp4` stays in the repo.

**Homepage media**: Publication thumbnails live flat in `assets/`, each named after the work (e.g. `dimo.mp4`, `unimate.mp4`, `ttt-parkour.mp4`, `vr-robo.mp4`). Affiliation/company logos carry a `-logo` suffix (`meta-logo.png`); `princeton-logo.jpg` doubles as the favicon and the navbar brand mark. Poster PDFs sit alongside them. Every file in `assets/`, `dimo/assets/` and `unimate/assets/**` is currently referenced (the one exception is the untracked `unimate/assets/UniMate.pdf`) — there are no orphans, so an unreferenced file is a mistake, not spare inventory.

## Indexing

Search-engine visibility is set **per page**, and the pieces interact — read this before touching `robots.txt`, `sitemap.xml`, or a `robots` meta tag.

| Page | `robots` | `canonical` | In sitemap |
|---|---|---|---|
| `/` | (none — indexable) | `linzhanmou.com/` | yes |
| `/dimo/` | `index, follow` | `linzhanmou.com/dimo/` | yes |
| `/unimate/` | `index, follow` | `linzhanmou.com/unimate/` | yes |
| `/resume/` | `noindex, nofollow` | **none, on purpose** | no |

- **`/resume/` is kept out of search results, but stays crawlable in `robots.txt`.** These two mechanisms conflict if combined: a `Disallow` stops the fetch, so the `noindex` is never read, and the URL can linger in the index as a bare link. Crawling must be allowed for the tag to work. `resume.pdf` is the one path `Disallow`ed outright, because a PDF cannot carry a meta tag and Pages cannot send `X-Robots-Tag`.
- **No `canonical` on `/resume/`** — `canonical` asserts "index this URL", which contradicts `noindex`.
- `/resume/` and `resume.pdf` are **unlinked from the entire site** (the homepage's Resume nav link is commented out, and nothing links the PDF). They are URLs you have to know.
- The `google-site-verification` meta lives in `index.html`.
- Keep `sitemap.xml` and the meta tags in agreement: a `noindex` page must not be listed.
- **Update a page's `<lastmod>` when you change that page.** It is a recrawl signal: a stale date says "settled, don't bother", which is exactly wrong after an edit, and a date bumped without a real edit trains Google to ignore the field. Take it from `git log` on the page's file. Two traps: XML comments **cannot contain a double hyphen** (so no git flags pasted into them — this silently broke the file once), and the date must be `YYYY-MM-DD` and not in the future. Validate with `xmllint --noout sitemap.xml` before pushing.

Self-contained, custom-designed project page for the DIMO paper — no Bootstrap, no shared assets, no `?v=` cache busting. All styling is in `dimo/css/style.css` (design tokens at `:root`); markup is in `dimo/index.html`; the only script is `dimo/js/nav.js`. Loads Academicons, Font Awesome 4, and the Inter / Newsreader / Space Grotesk / Space Mono fonts from CDNs. All media lives flat under `dimo/assets/` — `teaser.png`, `pipeline.png`, `interpolation.mp4`, `language.mp4`, `spinner.svg` (used as the two videos' `poster`), `favicon.svg`. There is no `dimo/img/` dir and no paper PDF in the repo: the arXiv, poster, and video buttons all point off-site, and `#demo` is a YouTube `<iframe>`.

- **Design system**: a dark "latent-space" hero over a light "paper" body. Tokens split the same way — `--space*` / `--on-space*` for the hero, `--paper*` / `--ink*` / `--line` for the body — plus a reserved blue→violet→pink `--spectrum` gradient used **only** on the title, the active nav node, the nav progress fill, and `favicon.svg`. Sections (`#demo`, `#applications`, `#abstract`, `#method`, `#poster`, `#cite`, in DOM order) alternate `.section` / `.section--alt` for a white / `--paper-2` tint (no borders). Each header is a mono `.kicker` + a `.section-title`.
- **Signature**: the hero figure is an inline SVG (`.field`) where one origin keypoint fans into five trajectories ending in CSS/SMIL-animated stick-figure skeletons (wave/walk/kick/jump/turn). Limbs rotate via `transform-box: view-box` with per-limb `transform-origin`; `prefers-reduced-motion` freezes them and hides the traveling `.kp` dots.
- **Side nav** (`.sidenav`): a fixed vertical "trajectory" rail in the left gutter, right-anchored so labels never crowd the content; **hidden below 1480px** (`@media (max-width: 1480px)`). `nav.js` uses one `IntersectionObserver` to reveal it once the hero leaves the viewport and another (`rootMargin: -45%/-50%`) to set the `.is-active` node and drive the `--nav-progress` spectrum fill. Links are plain anchors, so it degrades without JS.

Self-contained project page for the UniMate paper ("One Unified Model to Animate Diverse Skeletons", SIGGRAPH Asia 2026). No Bootstrap and no `?v=`. Public and indexable (see the Indexing table); `[arXiv]`, `[Dataset]`, and `[Twitter]` are present but `class="disabled"` placeholders.

```

  prompts.json          one prompt per glb, keyed by filename (see Prompt labels)
  css/style.css         the page stylesheet, 11 numbered sections
      schematics.css    the Applications figure system (layout · rig · motion)
  js/  viewer.js        Three.js engine for the interactive viewer
       examples.js      its stage catalog (data only)
       gallery.js       gallery scroll buttons + play-only-what-is-visible
       toc.js           TOC rail: scroll-spy + collision watcher
  glbs/                 the 40 rigs
  assets/  videos/      the 15 demo/result clips
           posters/     one poster frame per clip, same basename
           logos/       princeton.png · ucb.svg · mit.png
           favicon-baymax.png
```

The layout mirrors `dimo/` (`css/` + `js/` + `assets/`) so the two project pages read the same way. `assets/UniMate.pdf` is the one file nothing references — it is untracked, and 34 MB, so decide deliberately before committing it.

- **Design system**: ivory paper body over slate text with a terracotta accent. Palette tokens (`--ivory*`, `--slate-dark/-light`, `--accent: #d97757`) live in the `:root` block near the **top** of `css/style.css`, which is organized into 11 numbered sections. **One measure**: `.main-content` is 960px and *nothing* — prose, teaser, viewer, video — is wider. The galleries were the exception (full-bleed `100vw` around a 1150px track, so the clips ran ~200px past the prose); they are now in normal flow like any other figure and their track is the column. `--column` (`min(960px, calc(100vw - 2 * var(--page-gutter)))`) is that measure as a value, for the responsive clip sizes that used to be written against the viewport and so stood ~40px wider than the prose on a tablet; `--page-gutter` is `body`'s padding **plus the UA's 8px body margin**, and the phone block re-declares both together. Two gotchas: `--column` is off by the width of a classic scrollbar (`100vw` counts it, layout doesn't), so anything that must be exact takes a **percentage** instead — which only resolves if its box has a definite width, hence the `:has(> .gallery-video:only-child)` rule that takes single-clip rows off `max-content`. And `.video-gallery` carries no side padding: on a `max-content` row it would make the row wider than the track and a column-width clip would scroll by that much instead of sitting flush. Gotcha: `body` hard-codes `#fdfaf4` and `#1b1b1b` rather than using the tokens, so the page background is *not* `--ivory` — check which you mean before "fixing" one to match the other. `css/style.css` `@import`s Playfair Display (headings) + Roboto Mono (labels/mono) over a Georgia serif body.
- **TOC** (`.toc`): a fixed left-gutter rail, `display: none` until `@media (min-width: 1400px)`. It is a live progress rail, not just anchors — the scroll-spy in `js/toc.js` adds `.active` to the link for the topmost visible section. Anchors: `#examples`, `#abstract`, `#experiments` (+ `#diverse-skeletons-prompts`, `#one-prompt-diverse-skeletons`, `#diverse-prompts`, `#diverse-motions`), `#application` (+ `#motion-editing`, `#motion-inbetweening`, `#motion-expansion`).

Experiments runs as four numbered `.section-subtitle` blocks, all styled identically: §1 is the breadth gallery (`#diverse-skeletons-prompts`, `diverse-1–3.mp4`), §2–4 are controlled studies that hold one factor fixed at a time (prompt fixed / skeleton fixed / both fixed). §2–4 are **two-up**: their clips are `(100% - var(--gallery-gap)) / 2`, so a pair plus its gap is exactly the column and the strip always rests on two whole clips — they are comparisons, and half of a third clip read as a broken layout rather than as "more this way". §3/§4's third clip is one full page to the right. §1 keeps its own size (700px wide, tuned so the prompts baked into its 2x3 grids stay legible) and so still shows one clip and part of another. **Clip sizes are given as widths** (§1 700px, Applications 875px, §2–4 half the column), not heights: the clips are 1.75:1, and while the desktop rule set a height, the responsive clamp had to re-derive the width from it to the sub-pixel — the two drifted apart every time the border changed. §1 was twice given a treatment marking it as a lead-in rather than a peer — first an outlined box, then no number — and both read as broken rather than as a different rank; the user asked for plain consistency each time. Keep them uniform.
- **JavaScript** is four files, all in `js/`, and **`index.html` carries no behaviour of its own** — the only inline block left is the StatCounter snippet (project `12925377`, shared with the homepage) plus the importmap that resolves `three` to jsDelivr. `viewer.js` (the three@0.160.0 engine, an ES module) imports `EXAMPLES` from `examples.js` (data only). `gallery.js` and `toc.js` are plain scripts, each wrapping its work in one `DOMContentLoaded`. In `gallery.js`: the horizontal-scroll buttons navigate by *live* item position rather than a cached width, because a video's intrinsic size isn't known that early, and an `IntersectionObserver` (`threshold: 0.15`) plays only on-screen videos and switches every video to `controls` under `prefers-reduced-motion`. Scroll targets are **left-aligned, not centred** (`scrollTargetFor`) — on a two-up strip, centring the middle of three clips would cut both its neighbours in half. `stepIndex` then skips any index that resolves to the position the strip is already at: the last clips of a row share one clamped position, and stepping onto one would spend a click (or an auto-cycle beat) going nowhere. The three Experiments strips that hold more clips than fit (`autoCycle` in the gallery config — §1 `demoGallerySection`, §3 `promptGallerySection`, §4 `motionGallerySection`; §2 has exactly two clips and nothing to reveal) also **ping-pong themselves** while on screen (a page every `AUTO_CYCLE_MS`, 6s; the ends of the row flip the direction), so the row shows that it runs past both edges. The visitor always outranks it: any manual input — a nav button, or any scroll of the container itself — takes the wheel, and the cycle picks up again `USER_PAUSE_MS` (6s) after the *last* one, from wherever they left it (`yieldToUser`, which re-arms rather than stacking). It runs only while the strip is on screen and never under `prefers-reduced-motion`. The yield signal is deliberately the container's own `scroll`, not `wheel`/`touchstart`, which also fire when the visitor is merely scrolling the page past the gallery; `autoQuietUntil` covers the tail of the auto-scroll's own smooth glide, which outlives the existing 500ms `programmaticScroll` window — without it the cycle would keep pausing itself. In `toc.js`: `scrollSpy()`, and `collisionWatcher()` — the rail is fixed in the left gutter, so anything reaching past the text column runs under it, and the watcher fades the rail out (`.toc.is-eclipsed`) while that lasts. It measures the **clips**, not `.video-gallery-container`, which is the full column and so wider than the clip on the single-clip Applications galleries. It fired constantly when the galleries were full-bleed; now that they are capped at the column it only fires in the first few px above the rail's own 1400px breakpoint, and stands as the guard if a gallery is ever widened past the column again.
- **Figure edges**: the gallery clips carry a **1.5px `var(--slate-light)` frame**; the **teaser carries none**. The frame is load-bearing, not decoration: the renders are white to the pixel at all four edges (measured off the poster frames) against a `#fdfaf4` page — 1.03:1 — so the only thing separating a clip from the paper is the drop shadow, which is offset 4px *down*: the bottom edge reads and the top dissolves, taking the caption baked into the clip with it. The teaser is exempt because it runs the full column directly under the title block, where a frame boxes in the first thing on the page; the clips sit in rows, where figures have to be told apart from each other. Two settings were tried and rejected on the way here: a `1px var(--rule)` hairline (too faint to hold a row together) and `1.5px solid #000` — pure black is the same ink as the `.section-subtitle` plate directly above each strip, and stacked under one it reads as a fence. An inset `box-shadow` ring was also tried, to keep the border box out of the size math; it does not paint over `<video>` replaced content, so it is invisible. `.viewer-wrapper` is still `1.5px solid #000` — the last pure-black frame on the page.
- **Application schematics** (`css/schematics.css` + inline SVG in `index.html`): each of the three Applications clips runs in an `.app-row` beside a portrait **plate** — the clip is the evidence, the drawing is the claim. The plate carries the clip's own frame and stretches to its height, so the two read as a pair of figures; the clip takes what the row leaves (~696px, near enough to §1's 700 that they read as one size). **One convention across all three, and it is the only thing the tasks differ in: ink is what you hand the model, accent is what it returns.** Editing splits one figure (held spine/legs vs resampled head/arms — the held half runs the source's gait *in phase*, which is the claim made visible), in-betweening splits a timeline (two still key poses, three sweeping between), expansion is a **chain**: three prompts, three *different* motions, and each motion begins in the pose the one above it stopped in — that shared pose is the only thing joining them, so it is what the plate is built to show. **On the expansion plate colour is a state, not a class**: a figure is accent while its motion is being generated and turns to ink the moment it stops, so exactly one figure is ever coral. That reads the palette differently from the other two plates (accent = the model's output *now*, rather than the model's output), and it only works because that plate's bones and joints inherit the group's `stroke` instead of carrying `.dg-gen` themselves — check that if you add a rig to it. Kept in **its own sheet on purpose** — it is a self-contained figure system, and `style.css` shouldn't carry it; the only shared surface is `:root`, which is also why the SVGs are inline rather than assets (an `<img>` is a separate document and inherits none of the palette).
  - **The expansion plate runs its own clock**: one 9s master, three 3s turns. Each figure's tracks walk through the first third and then **hold** — the hold is what "that motion has stopped" looks like — and figures 2 and 3 are the same clock started 3s and 6s in, so they can never drift. The three motions are *different*, and named on their chips so the reader can check the drawing against the word — **1 · walks** (two strides, stopped dead mid-step), **2 · jumps** (crouches out of that step, launches, lands, settles), **3 · waves** (right arm up from the settle, hand swinging). They are authored as explicit per-bone stop tables in `schematics.css`, where **each motion's last pose is the next one's first** — edit a motion's opening stop and you must edit the previous one's closing stop with it, or the chain comes apart at that seam; `animation-fill-mode: both` is what makes the seam work, since a figure holds its opening pose all through its delay — appearing already in the pose the figure above it is holding. The progress bar fills a third per turn, by animating dash **length** (`stroke-dasharray: 0 1 → 1 1`) rather than `dashoffset`: on a `pathLength="1"` stroke an offset of 1 doesn't hide the dash, it slides the pattern's next repeat onto the path's final point, which showed up as a stray dot parked at the bottom of the plate. Two hairline ticks mark the seams.
  - **Motion** on the other two plates runs on two clocks: a 6s argument (the accent axis draws itself via `pathLength="1"` + `stroke-dashoffset`, then the generated poses land on it in order) and the figures' own 1.4s gait / 3s sweep. Every limb is two bones with a joint, each bone on its own track — the shin lags the thigh and flexes only on the lift, the forearm lags the upper arm, the body bobs twice per stride. Contralateral limbs share one keyframe track offset by half a period; `--dg-phase` shifts every bone of one rig at once, which is what makes a column of figures read as one motion at successive moments. All offsets are **negative** delays so nothing starts from a dead pose.
  - **The figure is the paper's rig representation**, not a stick man: every articulation is a joint node and every bone is the segment between two of them — root · chest · neck · head, plus shoulder/elbow/hand and hip/knee/foot per limb (13 joints, 12 bones, local box 44×66). Joints are hollow with a paper fill so a bone passing under one is punched out; the **root node is solid**, echoing `.venue-rig-root` in the masthead mark. A limb's own joint is drawn by its **parent**, never inside the rotating group — see the pivot rule below.
  - **The trap that cost a rebuild**: `transform-box: view-box` resolves `transform-origin` against the **root viewBox**, not the rig's local space — inside a translated, scaled group every pivot lands off the body and the limbs fan out from nowhere. The bones are therefore drawn so each joint *is* a corner of that bone's own box, and the pivots are `transform-box: fill-box` + `100% 0%` (left side) / `0% 0%` (right). It holds for the two-segment chains because the forearm never swings past the shoulder's x, so the corner is a fixed point even while the elbow moves. Keep that true when editing a pose. `vector-effect: non-scaling-stroke` keeps the line weight identical across the 0.8/0.85/1.4 rig scales.

The clips are also the **record of the original prompts** — several caption the same rigs the viewer loads (see Prompt labels).
- **Three.js viewer**: a live interactive viewer whose scene list is a stage catalog in `examples.js` (`EXAMPLES`) — labelled stages "Bipedal", "Articulated", "Flower", "Zoo", "Humanoid Robot", "Quadruped Robot", "Baymax Robot", "Eagle", "Shark", "Michelle", each laying out one or more of the 40 rigs in `unimate/glbs/*.glb`. `examples.js` has a documented per-stage option vocabulary (`spacing`, `rowSpacing`, `scale`, `pad`, `lighting`, `evenGaps`, `sizeBy`, `stagger`, …) — read its header comment before adding a stage; layout tuning belongs there, not in the engine. `viewer.js` normalizes, grounds (a port of a Blender pipeline), and renders them, exposes a lil-gui toolbar (geometry / skeleton / prompts / wireframe / speed / reset view — ground shadows are always on and deliberately have no toggle), and accepts drag-and-drop of `.fbx`/`.glb`/`.gltf`. Every `.glb` is referenced — do not delete them.
- **Prompt labels**: each model carries the text prompt its motion came from, drawn as an annotation on a figure plate in the page's own rig vocabulary — a mono **chip**, a tapered hairline **leader**, and a small **terminal** dot where it lands. The whole connector is one neutral material — tinted ink, no accent. It was drawn in the page's rig vocabulary at one point (a bone between hollow joint nodes, echoing the venue mark and the sidebar spine) and the accent ring had to go: on a scene this quiet it was the only saturated thing in frame and read as a UI hotspot stuck onto the render. The leader is tapered from nothing at the chip to its full weight at the rig, so it never rules a hard line into the type, and it stops `PIN_RADIUS` short of the terminal rather than running through it.

Where the terminal sits took three tries, and the middle answer is the one to keep. At the rig's **centre** it was always on the creature but the leader had to cross half a body to reach it — length is what makes these read as tethers rather than labels. At the **box edge** the leader was short but the mark hung in mid-air, because a static box spans the whole clip and its edge is empty for anything that flaps. So the mark travels from the centre toward its chip and stops at `MARK_INSET` of the way out: still inside the silhouette, most of the distance gone. Slot scoring charges for distance too (`LEADER_COST`, in chip-areas per 100px) — without that term the solver happily buys a clear patch of floor with a leader half the frame long. **How much it charges depends on how crowded the stage is.** `spread` runs 0 at four chips to 1 at nine: on a roomy stage every chip sits tight against its own rig, and as the count climbs the distance charge halves, the side/corner penalties fall away, and a candidate standing clear of every rig on the stage — out in the left or right margin — earns `MARGIN_BONUS` back. That is what lets the Zoo's outermost rigs put their labels in the empty flanks instead of nine chips competing for the same middle band. **`MARGIN_REACH` then caps how far out that goes** — a chip's outer edge may pass the outermost rig by 40px and no more (`spanX`, applied to every horizontal placement including the toolbar dodge and the sideways escape). The margins are there to relieve a jam, not to be occupied: without the cap the chips ran to the canvas edges and the picture read far wider than the group actually is. Zoo chips now span 89–627px of a 759px canvas, down from 14–744. The Bipedal stage, with four rigs, is unaffected by any of this. Median leader on the Zoo is ~46px, against ~148px before these two changes. Both ends are **static** under a still camera: the mark is a fixed point in the pivot's local frame and the chip is placed off the clip's whole envelope. A version that tracked the live pose so the joint stayed on a flapping wing was tried and removed — a marker that twitches along with the animation reads as noise, and the joint's whole job is to be the calm end of the bone. When placement leaves a chip over its own model's edge there is nothing to span, and both bone and joint are dropped (`#viewer-labels`, a click-through overlay inside the viewer; styled in `css/style.css` §8, positioned by `updateLabels()` every frame). The leader is load-bearing, not decoration: chips dodge each other, so without it a lifted chip would read as belonging to whatever it ended up over. The whole layer hides while the camera is being moved — pointer-down through release for orbit/pan/pinch, and for wheel zoom from the first notch until `ZOOM_REST_MS` after the last one, which outlasts the controls' damped glide so the chips reappear against a camera that has stopped rather than re-solving through the tail of the zoom. The text is **content, so it lives in `unimate/prompts.json`** (beside `glbs/`, not inside it), keyed by glb filename — edit prompts there; `examples.js` only carries a per-file `prompt` when one stage needs to override the shared line (`''` suppresses a label). House style for the copy is **the paper's own captioning format** (Appendix A.5, in `assets/UniMate.pdf`): `'An [object type] [action].'` — one sentence, under 12 words, one dominant action, a direction only where clearly observed, no adverbs, and the object named concretely ("A robot", "An eagle") rather than as "An object". Never invent a prompt from a filename — there are two ways to find out what a clip actually does, and `prompts.json` records which one each line came from (`_from_caption` = the original prompt; everything else = written from the motion). **First**, 23 of the 40 are captioned in the videos themselves: `assets/diverse-1..3.mp4` and `prompt-eagle/-shark/-bighero.mp4` caption the same rigs the viewer loads, so pull a frame with ffmpeg — the `posters/*.jpg` are t=0, before the caption types in, so they are blank. **Second**, for the rest, look at the animation: Blender is installed (`/Applications/Blender.app/Contents/MacOS/Blender -b -P script.py`), and a headless pass that imports each glb, samples the armature (net travel, rise, yaw, per-limb activity — all in body-height units) and renders a 6-frame filmstrip settles it in one run. That pass is what corrected the guesses: `ironman-walk` and `quadruped` walk **in place** rather than forward, `whale` never travels (only its tail sweeps), `whale` never travels (only its tail sweeps), and `dragon-fire` hovers rather than breathing fire. Three gotchas if you redo it — the mechs are near-black, so render `color_type = 'SINGLE'` or they are unreadable silhouettes; the clip name is `Reconstructed_Action` for every rig, so the file itself tells you nothing; and a render shows you the motion but **not the dataset's word for it**, which is the failure mode that actually bit. The prompt set reuses a small vocabulary, so reach for a verb already attested in `_from_caption` before coining a precise one: the chicken's head dip and the stego's rear-up read as "pecks at the ground" and "rears and swings its tail", but both are the same "attacks forward" that captions the piranha plant, and the monster's creep is "walks in place". Chips are sized (`max-width: 250px`) to keep a prompt in that format on one line — the forty read as a series only while none of them wrap. Chip placement is a small annotation-layout solver, and every piece of it is load-bearing. **Four slots**: each frame every rig is projected to a screen box (`screenBox`, from the local box `groundAndNormalize` stashes on the pivot) and the chip's four candidate positions — above, below, left, right — are scored by how much *model* each would cover, plus a preference (above is free, below costs a little, a side slot more, and a side slot pointing back INTO the group most). The cheapest wins, so a two-row diorama sends the front row's chips onto the empty floor and the back row's into the empty sky, while a rig at the end of the group puts its chip out into the margin beside it. The toolbar is scored as an obstacle too (`GUI_COST`) — without that, a chip whose rig sits under the panel picks "above", collides, and gets shoved clear across the frame. The choice is sticky (`SLOT_HYSTERESIS`) so an orbit through a near-tie doesn't make chips hop. **Escape**: collisions are resolved near→far, along the chip's own axis, with each step taken only if it can *actually* clear the blocker — a move clamped short of clearing leaves the overlap and spins the loop. The chain is: out along the axis within `MAX_LIFT` → slide across → overrun the cap → cross to the far side → and a last-resort stepped search from the rest position. **Baseline snap**: chips in the same slot within `BASELINE_SNAP` of each other align on one line, so rigs of different heights don't give every chip its own level. **Damping**: positions ease toward their target (`SETTLE_TAU`), so a slot flip or a resolved collision glides instead of teleporting mid-orbit; `SETTLE_SNAP` takes big jumps instantly, and `prefers-reduced-motion` skips the easing. **Chips recede with depth** — opacity and scale fall off with distance, measured as a *fraction* of the nearest chip's distance (`DEPTH_SPAN`), which lets a side-by-side row stay uniform while a second row drops behind. Two stages carry a deliberately generous `pad` (Zoo 1.35, Humanoid Robot 1.3) purely to give the label bands somewhere to live; tighten either and the chips are squeezed against the canvas edge. Note the leader's offsets and length are divided by the chip's scale, since it is a child of the chip and would otherwise stop short of its pin. Four things the placement does that are easy to undo by accident: chips are clamped inside the canvas and out of the toolbar's column (they are opaque and would eat each other's text), a near→far pass lifts colliding chips apart (capped at `MAX_LIFT`, which the 9-model Zoo actually reaches), box sizes are **cached** (`measureLabels`) rather than read per frame so anything changing a chip's size must re-measure (resize, webfont load, and toolbar collapse already do), and the anchor rides the **75th-percentile** per-frame mesh top, not the max — the max is set by one extreme frame (a backflip's peak) and pinning to it parks the chip a body-length above the rig for the whole rest of the clip.
